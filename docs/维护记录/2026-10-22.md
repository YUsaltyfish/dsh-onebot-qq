## 变更 1：QQ 登录状态真实检测

### 背景 / 现象

群里机器人实际已经收不到、发不出消息，但控制台「总览」「NapCat 连接」页都显示 **QQ 已登录**，没有任何提醒。
NapCat 进程和 WS 连接都正常，`get_status` 返回 `online: true`，`get_login_info` 仍返回账号昵称。

### 根因（分两层，第一版修复也踩了坑）

1. **旧逻辑根本不查登录状态**：控制台的"在线"判断是
   `Boolean(selfId) && !stale` —— `selfId` 是连接成功那一瞬间缓存的，之后只看 WS 心跳。
   WS 心跳只能说明 **NapCat 活着**，不能说明 **QQ 账号在线**。
2. **第一版修复（用 `get_login_info`）也无效**：QQ 掉线后 NapCat 仍返回缓存的 `user_id` / `nickname`。
   同理 `get_status` 的 `online` 取自 NapCat 内部 `selfInfo.online`，只在"被踢下线 / 主动退出"时置 false，
   **网络异常导致的掉线不会更新**。
3. **最终方案：用需要 QQ 服务端往返的 API 探测**，例如 `get_stranger_info`：
   - 在线：`retcode = 0`、`status = "ok"`；
   - 离线：`retcode = 200`、`status = "failed"`、`wording = "Cannot read properties of null (reading 'coreInfo')"`。

   （旁证：同时期 NapCat 日志里发消息持续报
   `EventChecker Failed ... "result":1006514,"errMsg":"网络连接异常!"`。）

### 代码变更

#### 1.1 `kernel/napcat-adapter.js`（主要改动）

新增常量：

```js
/** QQ 登录状态主动探测间隔（WS 连着不代表 QQ 在线：NapCat 可能仍保持心跳）。 */
const LOGIN_CHECK_MS = 30000
/** 同一检测结果的缓存时间，避免控制台 5s 轮询频繁打 NapCat。 */
const LOGIN_CHECK_TTL_MS = 10000
```

构造器新增状态：

```js
// QQ 登录状态（主动探测）：NapCat WS 连着但 QQ 掉线时，靠它发现并提醒
this.loginOk = null
this.loginCheckedAt = 0
this.loginError = ''
this._loginTimer = null
this._loginChecking = null
```

`connect()` 启动轮询，`close()` / `onclose` / `_forceReconnect()` 重置状态：

```js
async connect() {
  this.closed = false
  this._startLiveness()
  this._startLoginWatch()   // 新增
  this._open()
}
```

`health()` 新增三个字段：

```js
qqLoggedIn: this.loginOk,              // null=未知/检查中，false=WS 在但 QQ 不在线
qqLoginCheckedAt: this.loginCheckedAt || null,
qqLoginError: this.loginError || '',
```

新增 `checkLogin()`（核心）：

```js
async checkLogin({ force = false, quiet = false } = {}) {
  // 1) 10s 缓存（控制台 5s 轮询不应每次都打 NapCat）
  // 2) 并发去重：_loginChecking
  // 3) 先 get_login_info 拿 selfId（掉线时可能拿到缓存值，只用来确定账号）
  // 4) 真·在线探测：get_stranger_info（HTTP 优先，失败再 WS）
  const probeOk = Boolean(probePayload && probePayload.status === 'ok' && Number(probePayload.retcode) === 0)
  // 5) probeOk → loginOk=true / loginError=''
  //    否则   → loginOk=false / loginError=<wording 或兜底文案>
  return { ok, selfId, nickname, error, checkedAt }
}
```

新增 `_startLoginWatch()`：连接期间每 30s 静默调用一次 `checkLogin({ quiet: true })`；
`_fetchLoginInfo()` 改为复用它：

```js
async _fetchLoginInfo() {
  return this.checkLogin({ force: true, quiet: true })
}
```

#### 1.2 `index.js` — `kernel.checkNapcat()` 重写

- 先 `await napcat.checkLogin({ force: true })`；
- 返回体新增 `qqLoggedIn` / `qqLoginCheckedAt` / `qqLoginError`；
- **NapCat 连着但 QQ 不在线 → `ok: false`**，错误文案带原因；
- NapCat 未连接 → 仍返回 `ok: false`（区分"NapCat 未连"和"QQ 掉线"）。

#### 1.3 `admin/endpoints.js` — 状态透传

`napcatStateOf()` 与 `status.health` 各新增：

```js

qqLoginCheckedAt: health?.qqLoginCheckedAt ?? null,
qqLoginError: toStr(health?.qqLoginError),
```

#### 1.4 `client.js` — 控制台展示

- **总览状态栏**：新增 `QQ 已登录 / QQ 未登录 / QQ 检查中 / QQ 未知` 徽章
  （`title` 显示失败原因）；
- **总览红色提醒条**：`health.napcatLinked && health.qqLoggedIn === false` 时置顶显示
  「🔴 QQ 账号已掉线（NapCat WS 还连着）…原因…」；
- **总览新增「检查 QQ 登录」按钮** + 「最近检查 HH:mm:ss」：立即强制探测；
- **NapCat 连接页**：改用同一份登录状态，按钮改为「🔌 测试连接 / 检查登录」，
  提示文案区分三种情况（未连接 / 检查中 / 已掉线）。

### 接口变化（向后兼容）

| 位置 | 新增字段 | 说明 |

### 验证

- 真实 NapCat 实例（QQ 已掉线）：

  旧逻辑此时会返回 `ok: true`（对比确认）。
- 仓库根目录 `node --test`：**189/189 通过**（本机跑）。

### 已知限制 / 待办

- 探测固定用 `get_stranger_info`（无消息副作用），30s 一次；如嫌频繁可把 `LOGIN_CHECK_MS` 调大。
- 掉线只做"发现 + 提醒"，**没有做消息暂存/重发**；掉线期间入站消息本身也收不到，出站会失败并记日志。
- 若某天 NapCat 版本对 `get_stranger_info` 的离线返回形态变了，需同步调整 `probeOk` 判定；
  建议后续加一条"探测失败但 WS 正常"的 fallback（例如再试 `get_status.online`），避免误报。
- `client.js` 无自动化测试，UI 需人工验收。

## 变更 2：主动接话「冷场找话」开关

### 背景 / 现象

群长时间没人说话时，机器人会被定时拉起"主动找话"，多数回合选择静默，日志里出现连续多轮
「[主动接话候选] … 这轮不发送」「继续静默」。用户期望：**只有群里出现新消息时才考虑接话**。

### 根因

主动接话有两条触发路径：

| 路径 | 触发方式 | 代码位置 |
|---|---|---|
| 话题接话 | 入站消息驱动，按语境打分 ≥ 阈值才接 | `consider(ev)`（`kernel/pacing.js`） |
| **冷场找话** | **每 30s `tick()`，群安静超过 `coldSilenceMs` 就直接起一轮** | `tick()`（`kernel/pacing.js`） |

第二条与"有没有新消息"无关，所以群里安静反而更容易触发。

### 代码变更

#### 2.1 `kernel/pacing.js`

新增默认值：

```js
export const REPLY_DEFAULTS = {
  ...
  coldSilenceMs: 180000,
  silenceEnabled: true,      // 冷场找话：关 = 只在群里有新消息时才可能接话（不定时找话）
  ...
}
```

新增判定 + 两处短路：

```js
/** 冷场找话是否开启（关 = 只由入站消息驱动「话题合适时接话」，不再定时找话）。 */
const silenceOn = () => cfg.reply.silenceEnabled !== false

function tick() {
  if (!silenceOn()) return
  ...
}

function start(opts = {}) {
  ...
  if (!proactiveEnabled()) return null
  // 冷场找话关掉时不需要定时器：接话机会只由入站消息触发（topic 路径）
  if (!silenceOn()) return null
  timer = setInterval(() => { ... }, 30000)
}
```

启动日志同步：

```js
+ (silenceOn() ? `冷场≥${...}分钟` : '只在群里有新消息时接')
```

> 注意：`silenceEnabled=false` 时**连 30s 定时器都不装**（不再空转），`topic` 路径完全不变。

#### 2.2 `kernel/config-store.js`

`defaultConfig().pacing.reply` 增加 `silenceEnabled: true`（保持旧行为为默认，避免影响其他部署）。

#### 2.3 `admin/schema.js`

「主动接话」页新增控件（放在「群里安静多久算冷场」之前）：

```js
{
  key: 'pacing.reply.silenceEnabled', group: '主动接话', type: 'bool',
  label: '群冷场时也主动找话', default: true,
  hint: '开 = 群里长时间没人说话也会主动起个话头；'
      + '关 = 不再定时找话，只有群里出现新消息、且语境合适时才可能接一句。',
}
```

#### 2.4 `docs/配置参考.md`

`pacing.reply` 表格新增 `silenceEnabled` 一行，并把 `coldSilenceMs` 标注为「仅 `silenceEnabled=true` 时生效」。

### 实例配置变化（不进仓库）

本机实例配置（`<dataDir>/config.json`）已设：

```json
"pacing": { "reply": { "silenceEnabled": false } }
```

效果：两个已允许主动接话的群**只在有新消息时才可能接话**；长时间静默不再产生任何主动回合。

### 验证

- `node --test` 189/189；
- 行为矩阵：

| `reply.enabled` | `silenceEnabled` | 定时器 | 冷场找话 | 话题接话 |
|---|---|---|---|---|
| false | — | 不装 | 无 | 无 |
| true | true（默认） | 30s | 有 | 有 |
| true | **false** | **不装** | **无** | 有（消息驱动） |

### 已知限制 / 待办

- 关掉冷场后，"群里彻底没人说话"时机器人永远不会主动开口——这是本次的**预期行为**。
- 若以后想两者兼得（冷场偶尔开口但别太频繁），可把 `silenceEnabled` 打开并调大 `minGapMs` / 减小 `hourlyMax`，
  或后续加"每天冷场次数上限"。

## 变更 3：群记忆自动积累内置化（含频率开关）〔已复原〕

> ⚠️ **本变更已于 2026-10-22 复原**：代码回退到 `3df2991` 的状态（群记忆仍只读），
> 原因是重新评估"积累器应该作为独立子插件还是写在 group-memory 内"，决定先把方案定下来再实现。
> 本节与补丁保留，作为设计/实现留档；重新实施时可直接参考。

### 现象

所有群记忆文件停在 **2026-10-20 20:32**，之后不再更新；控制台「群记忆」页「立刻积累一轮」也报
「本机未配置群记忆积累能力」。

### 根因

- 旧版自动积累 = 系统 cron（每天 04:30/12:30/20:30）执行 `group-memory.sh` → 调 `/opt/bridge/group-memory.py`；
- 该 python 积累器位于旧架构目录，**在切换新版插件、清理旧架构时被删除**；
- 于是 cron 每轮稳定失败：`python3: can't open file '/opt/bridge/group-memory.py'`（日志里 10-21 起全是这个）；
- 新版 `group-memory` 子插件按设计**只读**（"积累是独立进程/cron 的事"），而本机又没有
  `ops.local.mjs`（`ops.memoryAccumulate` 未实现）→ 首次成功积累停在 10-20 20:32:18。

### 方案

把积累器**内置到插件**（不再依赖 cron / 外部脚本），并给出控制台可调的开关与频率。

#### 3.1 内核能力：`dsh.runIsolatedTask()`（`kernel/dsh-driver.js`）

新增一个"独立的一次性后台会话"：

```js
async function runIsolatedTask({ name, prompt, timeoutMs = 10 * 60000, cwd })
  → { ok, sessionId, text, reason }
```

- 用 `ctx.sessionController.create({ cwd })` 建临时会话（`cwd` = 数据目录，**不挂 QQ 工作区**、不进 `sessions.json`）；
- `sessionController.prompt()` 提交 → 等该会话 `turn/end` → `inspect()` 取最后一条 `assistant/message` 的文本；
- 完成后 `archive()` 清场；超时/失败同样归档。

安全护栏（`index.js`）：

- `kernel.maintSessionIds`：后台任务会话 id 集合；
- 原生工具 `execute()` 入口**一律拒绝**这些会话的调用
  （`后台任务不允许调用工具：请直接输出文本结果`）——从结构上避免积累任务误发 QQ 消息；
- 临时会话用 qq-chat preset（工具面已裁剪），`cwd` 也不在 QQ 工作区，双重隔离。

#### 3.2 插件：`plugins/group-memory/index.js` 内置积累器

配置项（控制台「群记忆」→「工具配置」自动渲染）：

| 键 | 默认 | 说明 |
|---|---|---|
| `accumulateEnabled` | `true` | 自动积累总开关 |
| `accumulateIntervalHours` | `8` | 间隔（小时） |
| `accumulateLookbackHours` | `8` | 回看最近多少小时留档 |
| `accumulateMsgPerGroup` | `200` | 每群最多取多少条 |
| `accumulateMaxChars` | `8000` | 每群正文上限（字符） |
| `accumulateMinNewMsgs` | `20` | 少于多少条就跳过（省 token） |
| `accumulateRetainRevisions` | `20` | `.revisions/` 保留份数 |

流程：

1. 每 60s 检查一次是否到期（`state/group-memory.json` 记 `lastRunAt`；首次启动留 5 分钟缓冲）；
2. 群清单 = `logs/qq_chat/group_<群号>.jsonl*` 出现过的群 ∪ 已有 `qq-memory/<群号>.md` 的群；
3. 每群读最近 `lookbackHours` 内、最多 `msgPerGroup` 条消息（`→` 标机器人出站），拼成正文（截到 `maxChars`）；
4. 组装提示词：当前记忆 + 最近聊天 + 输出要求（只输出完整 Markdown、认人只看 QQ 号、不编造、20000 字内）；
5. `runIsolatedTask()` 跑模型 → 清洗代码块围栏 → 校验（非空 / ≥30 字 / 含标题）；
6. `writeMemory()`（**唯一写盘入口**）：旧版备份到 `.revisions/<群号>-<YYYYMMDD>-<HHmmss>[-序号].md`
   → 按 mtime 只留最近 N 份 → 原子写回（0600）；
7. 单飞锁：上一轮没跑完不再起；单群失败不影响其它群；一轮最多 12 个群。

控制台/端点：

- 插件把能力挂到 `bot.shared`：`memoryAccumulate / memoryAccumulateStatus / memoryAccumulateSync`；
- `index.js` 的 `botProto` 新增只读 `get shared()`；
- `admin/endpoints.js`：`memory list` 返回 `accumulate` 状态与 `schedule` 文本（每 N 小时 / 上次结果 / 下次时间）；
  `memory refresh` **内置积累器优先**，没有才退回 `ops.memoryAccumulate`；
- `client.js` 群记忆页：状态行显示自动积累节奏，确认弹窗文案同步更新。

#### 3.3 运维清理

- 删除旧的 crontab 行 `30 4,12,20 * * * bash /root/group-memory.sh`；
- `/root/group-memory.sh` 与 `/var/log/group-memory.log` 归档到备份目录
  `21-旧群记忆积累器/`（旧 python 实现已随 `/opt/bridge` 删除，仅保留行为日志备查）。

### 验证

- 新增测试 `test/audit-group-memory-accumulate.test.js`（4 条）：
  消息够 → 调后台任务并写回；`.revisions` 保留 N 份并清理旧版；消息太少跳过不调模型；
  开关关闭 / 模型输出无效 → 不写盘。
- 全量 `node --test`：**193/193 通过**；`check-syntax` 58 文件 / `check-no-secrets` 68 文件 / `check-pack` 全绿。
- 详见本日补丁 `patches/2026-10-22-group-memory-accumulate.patch`。

### 已知限制 / 待办

- 真机首次积累需要重启 dsh-web 后触发（或控制台「立刻积累一轮」）；模型输出质量依赖所选模型；
- 每群一次模型调用，群多时耗时可观（串行、12 群/轮上限）；
- 后台会话会短暂出现在 GUI 侧栏（完成后归档）；若 `archiveSession` 不可用则留在「未分组」，不影响功能；
- 旧记忆里 `<!-- n=... -->` 记账注释在读取侧被剥掉，积累写回时**不会保留**（新版不再维护该账本）。

## 变更 4：按方案 B 重新实施群记忆积累（同插件内拆模块）

> 承接变更 3：功能恢复到 `18b6db8` 的行为，但**代码组织按方案 B**——积累实现不再塞在
> `plugins/group-memory/index.js` 一个文件里，而是拆成同目录 `accumulate.js`（写/调度），
> `index.js` 只保留读取侧并负责接线。**对外仍是一个子插件**：一组配置、一个控制台页面、两个开关。

### 结构

```
plugins/group-memory/
├── index.js       读取侧：before-turn 指针 / read_memory 工具 / 缓存；setup 末尾接线积累器
└── accumulate.js  写入侧：createAccumulator({ bot, cfg, log, dataDirOf, memoryDirOf,
                     readMemoryOf, invalidateMemoryOf }) → { status, trigger, manual, sync, start }
```

- 配置项仍在 `group-memory` 的 configSchema 下（`accumulateEnabled` / `accumulateIntervalHours` /
  `accumulateLookbackHours` / `accumulateMsgPerGroup` / `accumulateMaxChars` /
